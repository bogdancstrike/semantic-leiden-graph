# Semantic Leiden Explorer

Upload raw texts, and the system finds the topics in them by itself: every document is
embedded, linked to its nearest neighbours, and the resulting similarity graph is clustered
with weighted **Leiden**. You then explore the corpus through **semantic, keyword and hybrid
search**, community-aware routing, a graph view and per-community analytics.

Communities emerge from meaning alone, without labels or keyword lists. After discovery,
Gemini (default) or OpenAI automatically selects as many central community documents as
its context window can hold and produces
evidence-backed topic summaries. Run analysis daily or from the Communities page.

```
CSV / API  ─►  Elasticsearch  (content, metadata, BM25, highlights, facets)   ◄── source of truth
               Qdrant         (dense vectors, ANN, community-filtered search)  ◄── derived
               Neo4j + GDS    (k-NN similarity graph, Leiden, graph analytics) ◄── derived
```

## Quick start

```bash
cp .env.example .env            # change store passwords; set GEMINI_API_KEY for analysis
docker compose up --build       # first start downloads the embedding model (~470 MB)
```

Linux hosts: Elasticsearch needs `sudo sysctl -w vm.max_map_count=262144` (see
[specs.md §10.5](docs/specs.md#105-troubleshooting-the-stack)).

The `seed` container imports `data/sample.csv` (72 news-style texts in English and Romanian
across 10 topics) and runs Leiden once. Re-running it is idempotent.

| What | URL |
|---|---|
| Explorer UI | http://localhost:3000 |
| API + Swagger | http://localhost:8000/docs |
| Qdrant dashboard | http://localhost:6333/dashboard |
| Neo4j Browser | http://localhost:7474 (neo4j / `NEO4J_PASSWORD`) |
| Elasticsearch | http://localhost:9200 (elastic / `ELASTIC_PASSWORD`) |

All infrastructure ports bind to `127.0.0.1`; only the UI listens on all interfaces.

## What you can do

- **Topics** (`/topics`, with `/summaries` redirecting here): a live intelligence briefing
  of saved community analyses with narratives, cited named entities (NER), classifications,
  reporting sentiment and comparable-period trends. Search the analysis; filter by analysis
  date/time, sentiment, classification, report, rising or saved topics. Sort by recency, size
  or evidence coverage; save, export or delete a topic analysis. Every topic opens `/topics/{id}` with its graph snapshot, analysis, full community
  document search, and LLM activity (instructions, evidence, model and token budget).
- **Dashboard** (`/`): corpus health at a glance — KPIs, clustering quality and
  distributions, each tile and bar drilling into the documents or communities behind it.
- **Explore documents** (`/documents`): browse every document (exact Elasticsearch filter,
  sortable, paginated) or rank them:
  - *semantic* (Qdrant, cross-lingual), *keyword* (Elasticsearch BM25 with diacritic
    folding, fuzzy, phrase boost and a safe advanced syntax) or *hybrid* (RRF or DBSF fusion
    with a keyword/semantic balance slider);
  - **advanced conditions** built with a nested AND/OR/NOT query builder over text, id,
    source, community, length, dates and every metadata column — the same tree filters
    browsing, keyword search and semantic pre-filtering;
  - auto routing over the top-R anchors, MMR diversification, community facets and a
    per-result "why is this here" explanation; saved searches and CSV/JSON export.
- **Graph** (`/graph`): the similarity graph on a canvas — strongest links, chosen
  communities, a 1-2 hop neighbourhood, or the documents a search returns plus their
  neighbours — with an in-card navigator of descriptively named communities, direct focus/highlighting
  and analysis actions. Auto-arrange, community/force/circle/grid layouts, separation, labels,
  boundaries (direct Highlight communities toggle), zoom, pause, fit and PNG export make large views easier to explore.
- **Communities** (`/communities`): size, cohesion, density, conductance, central documents
  and neighbouring communities; "which communities discuss X?" topic search; metric
  conditions; **Analyze now** discovers topics and analyzes their top-k recent documents,
  with date/time period selection, automatic document sizing, job progress, report history and evidence.
- **Import** (`/import`): drag a CSV into the UI, map its columns (id, text, metadata, or
  generated ids) and follow the job; the progress survives leaving the page. Imports are
  upserts by `id`: re-importing changes nothing, edited rows are re-embedded, removed
  metadata keys disappear. **Run AI analysis after import** queues a linked Topics report for
  exactly the successful rows in this file, including unchanged reimports. Jobs report per-row errors. `docs/sample.csv` (30,000 synthetic
  rows, generated by `docs/generate_sample.py`) exercises it at scale.
- **Operations** (`/operations`): background jobs for Leiden (gamma/seed), graph rebuild
  (k/threshold) and *reconcile* (repairs Qdrant/Neo4j from Elasticsearch), clustering
  history, and **data sources** — delete every record of one import (e.g. `csv:sample.csv`)
  from all three stores. Graph/community actions send their document membership to analysis
  and open the resulting Topics report; document drawers link to related Topics.

## Automatic and on-demand community analysis

Set `GEMINI_API_KEY` in your local `.env` and start the stack. Gemini uses
`gemini-flash-latest` and the `generateContent` endpoint with `X-goog-api-key`.
Set multiple keys with commas in the same variable (`GEMINI_API_KEY=KEY_1,KEY_2,KEY_3`
or `OPENAI_API_KEY=KEY_1,KEY_2`). Rejected credentials, rate limits and transient provider
failures try another key, and subsequent requests retain the working key.
Provider keys stay on the backend; `.env` and local analysis state are ignored by Git
and excluded from Docker build contexts. The header’s API-key setting is the app’s
`API_KEY`, separate from provider credentials.

To use OpenAI instead, set `LLM_PROVIDER=openai` and `OPENAI_API_KEY`. The default
OpenAI model is `gpt-4.1-mini`; override `OPENAI_MODEL` or `GEMINI_MODEL` as needed.
OpenAI uses the Responses API with `store=false`. After editing settings, run
`docker compose up -d app` to recreate the API with the new configuration.

In **Communities → Community analysis**, documents per topic is automatic. Choose a
period (Last 24 hours, Last 7 days, Last 30 days, Custom range with date and time pickers,
or All time) and maximum topics (default 100), then click **Analyze now**.
The job continues when you leave the page. Expand a report’s topics to read summaries,
key findings, limitations, and the exact document excerpts sent to the provider.
Historical community IDs refer to the report’s clustering version; evidence links open
the current document, which may have changed or been deleted since analysis.

Each run:

1. Refreshes weighted Leiden over the whole similarity graph, using the active graph
   policy and minimum community size. Topic discovery does not require an LLM.
2. Selects documents whose **content `updated_at`** is in `[run time − lookback, run time)`
   in UTC (or the explicitly chosen period; All time has no lower bound). This includes new and edited documents, excludes future timestamps, and does
   not use publication dates stored in metadata. Reclustering does not change this timestamp.
3. Ranks those eligible documents in each community by weighted internal degree
   (sum of similarities to community members), with document ID as the deterministic tie-break.
   It keeps the largest centrality-ranked prefix that fits the LLM, with no fixed document-count
   cap. Older central documents cannot crowd out recent ones.
   Documents outside a community are counted but not sent for analysis.
4. Analyzes up to `ANALYSIS_MAX_COMMUNITIES` topics, ordered by eligible document count.
   Reports explicitly show skipped topics. Each selected document is limited to
   `ANALYSIS_DOCUMENT_CHARS` characters (default 4,000); truncation is shown in the report.
5. Discovers Gemini’s input/output limits and uses `countTokens` on the exact instructions
   and evidence, or uses tiktoken for OpenAI. It reserves `LLM_MAX_OUTPUT_TOKENS` for the
   response and `LLM_TOKEN_SAFETY_MARGIN` (default 1,024) for framing. `LLM_CONTEXT_TOKENS`
   can impose a smaller context limit and is required for OpenAI models other than the
   known default. If even one document cannot fit, its longest fitting excerpt is marked.
6. Sends one generation request per selected community and validates JSON summaries,
   narratives, sentiment and its explanation, classifications, named entities with supporting
   citations, and evidence IDs.
   Transient connection, rate-limit and server errors retry up to `LLM_MAX_RETRIES` (default 2).
   Failed topics preserve successful results and appear as a partial report. Empty windows
   finish without calling an LLM. Duplicate active analysis requests return HTTP 409.

In a topic dossier, the graph snapshot preserves up to 80 central evidence documents. Search
node text or IDs, select/unselect nodes, and right-click for details, live connections and related
topics; the Node actions button exposes the same menu. Document search covers full saved
membership. Named Entities provides counted appearances, document coverage, source distribution,
UTC update activity, example passages and co-occurrences, with sorting, filters and CSV export.
Counts cover exact-name matches in the analyzed evidence; aliases are not merged. Export a
Markdown briefing or the full evidence JSON. Deleting a topic removes its
saved analysis and membership while preserving corpus documents.

Trends compare a topic's share of recently updated documents across equal, non-overlapping
periods with the same scope/embedding model. Semantic centroid matching handles changing
community IDs. A share increase of at least 25% is rising, a decrease of at least 20% is falling
(with minimum counts); unmatched topics and all-time/import reports show unavailable. Trends
measure corpus activity, not verified internet popularity. Older reports lack newly added NER
and trend fields until reanalyzed.

Automatic analysis is enabled when the selected provider has a key and
`ANALYSIS_SCHEDULE_ENABLED=true` (default). The first scheduled run is 24 hours after
initial setup; subsequent runs are every `ANALYSIS_INTERVAL_HOURS` (default 24), always
covering the preceding **24 hours**. On-demand runs do not reset this schedule. The API
must be running; a missed due time runs after restart or after another background job
finishes. Missed historical windows are not replayed. Schedule checks run every 30 seconds.

Reports, graph/evidence snapshots, saved membership, and the next due time persist in SQLite on the Compose
`analysis-state` volume. Local execution uses `.state/analysis.sqlite3`, configurable via
`ANALYSIS_DB_PATH`. Interrupted reports become failed on restart, preserving their evidence.
Cancellation takes effect between steps or after the current provider request finishes.

| Endpoint | Purpose |
|---|---|
| `POST /jobs/analyze` | Start a job; `time_range`: `relative` (default), `custom`, or `all`; `lookback_hours` for relative periods; timezone-aware `window_start` and `window_end` for custom periods. Optional `community_ids` snapshots a graph selection, and `max_communities` limits topics. Legacy `top_k` remains an optional API cap. Requires the app API key when configured. |
| `GET /analysis/config` | Provider, model, input limits, readiness and daily schedule; no credentials. |
| `GET /analysis/runs?limit=20&offset=0` | Paginated report history, without document bodies. |
| `GET /analysis/runs/{id}` | Full saved report and evidence; explicitly deleted topics are removed. |
| `GET /analysis/topics` | Live topic summaries; supports `q`, `sentiment`, `classification`, `trend`, `created_after`/`created_before`, `sort` (`recent`, `documents`, `coverage`), `run_id`, `document_id`, repeated `topic_ids`, `limit` and `offset`. Date bounds filter analysis creation time. |
| `GET /analysis/topics/{id}` | Saved community analysis, graph snapshot, membership and LLM activity. |
| `GET /analysis/topics/{id}/documents` | Search current document content within saved topic membership; `q`, `limit`, `offset`. |
| `DELETE /analysis/topics/{id}` | Delete a saved topic analysis and membership; preserve source documents. Running reports return 409. Requires the app API key when configured. |
| `POST /documents/upload` | Multipart `run_analysis=true` queues an analysis of the successfully imported document IDs and returns its job/report links in the import result. |
| `GET /jobs/{id}` / `DELETE /jobs/{id}` | Progress and cancellation, using the existing job API. |

```bash
curl -X POST http://localhost:8000/jobs/analyze \
  -H 'Content-Type: application/json' \
  -d '{"time_range":"relative","lookback_hours":24,"max_communities":100}'
# Add -H "X-API-Key: $API_KEY" if app authentication is enabled.
```

See [.env.example](.env.example) for provider timeouts, retries, output limits and schedule
settings. Historical reports remain readable; reports made before membership or richer
LLM output was recorded show that limitation explicitly. API contracts follow [Gemini generateContent](https://ai.google.dev/api/generate-content)
and [OpenAI text generation](https://developers.openai.com/api/docs/guides/text).

## Tests

```bash
pytest -q                                      # unit/API tests; optional integrations skip without their environment variables
docker compose up -d qdrant                    # if the stack is not already running
QDRANT_TEST_URL=http://localhost:6333 pytest -q tests/integration   # real Qdrant, HTTP + gRPC
(cd frontend && npm test && npm run build)       # vitest + strict type-check + production build
(cd frontend && npx playwright install chromium) # once
(cd frontend && npm run test:e2e)              # isolated browser tests, including analysis + accessibility
(cd frontend && BASE=http://localhost:3000 npm run audit:a11y) # running Compose UI
```

The analysis tests cover both providers’ real HTTP request shapes using MockTransport,
time-window boundaries, top-k ranking, truncation, empty windows, unassigned documents,
provider errors, partial results, auth, cancellation, duplicate jobs, persistence and scheduling.
Browser tests cover automatic sizing, custom/all-time periods, Topics/detail/graph/search
flows, saved/date/classification filters, NER, exports, deletion, graph layouts and node
context menus, report/evidence rendering, reloading, missing keys,
provider errors and WCAG accessibility. They start an isolated Vite server on port 5178
and mock API responses, so they do not require infrastructure or provider credentials.

An optional test exercises real clustering, selection and LLM analysis against the running
Compose stack. It creates a persisted report using existing data and incurs one provider
request; it uses all time so a previously imported corpus can be used:

```bash
ANALYSIS_TEST_API_URL=http://localhost:8000 RUN_LIVE_LLM_ANALYSIS=1 \
  pytest -q -s tests/integration/test_analysis_stack.py
```

## Status and honest limitations

This is a proof of concept, hardened where it was cheap to do so. See
[specs.md §29](docs/specs.md#29-from-poc-to-production) and §24.1 for the gaps.

- **One process runs everything.** Jobs run in-process on one worker thread, so the API must
  run as a single process. Scale-out needs a shared queue.
- **Auth is a shared API key** on mutating routes. Use OIDC (Keycloak) for anything real.
- **Full-stack analysis is opt-in.** Unit/API tests use fake ES/Neo4j and real local Qdrant;
  optional server tests cover Qdrant HTTP/gRPC. The live analysis smoke test exercises the
  full Compose stack and configured provider. It is not part of default offline CI.
- **LLM output is based on samples.** Reports show the selected evidence and truncation;
  generated titles and summaries do not alter graph membership or search behavior.
- **Reports accumulate on disk.** Back up the `analysis-state` volume; automatic retention
  and multi-replica scheduling are not implemented.

For local single-node development on a large, mostly-used host disk, Elasticsearch’s
percentage watermarks can block system shards even with ample free space. If allocation
explain identifies `disk_threshold`, set absolute free-space watermarks for this local
cluster (for example low `30gb`, high `20gb`, flood stage `10gb`) through `/_cluster/settings`;
never disable disk thresholds or delete data to bypass the check.
